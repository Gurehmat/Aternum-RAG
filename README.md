# Aternum RAG

Lightweight RAG sandbox for Aternum-style nodes, blocks, tags, and future permission filtering.

## Stack

- FastAPI backend
- React + Vite frontend
- Postgres with pgvector
- `sentence-transformers` using `intfloat/e5-base-v2`

## Quick Start

Start Postgres:

```bash
docker compose up -d postgres
```

Run the backend:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
uvicorn app.main:app --reload --app-dir backend
```

The first ingest or search call downloads the Hugging Face embedding model.

Run the frontend:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

## Backend Shape

Main files:

- `backend/app/main.py`: FastAPI routes and response assembly
- `backend/app/database.py`: SQLAlchemy engine, sessions, `Document`, and `DocumentChunk`
- `backend/app/ingestion.py`: document ingest, Aternum node normalization, and ingest response mapping
- `backend/app/chunking.py`: text chunking
- `backend/app/permissions.py`: current search tag filters and production permission TODOs
- `backend/app/embeddings.py`: `intfloat/e5-base-v2` loading plus passage/query embedding helpers
- `backend/requirements.txt`: Python dependencies

Frontend files:

- `frontend/src/App.tsx`: the prototype console for ingesting text, searching, listing docs, and deleting docs
- `frontend/src/main.tsx`: React entry point
- `frontend/src/styles.css`: UI styling

Routes:

- `GET /health`
- `POST /api/documents`
- `GET /api/documents`
- `DELETE /api/documents/{document_id}`
- `POST /api/rag/query`
- `POST /api/integrations/aternum/nodes`

## How It Works

There are two ingest paths.

`POST /api/documents` is the manual prototype path. The frontend uses this when you paste text into the UI. The request body is validated as `IngestDocumentRequest` in `backend/app/ingestion.py`.

`POST /api/integrations/aternum/nodes` is the Aternum-shaped path. It accepts nodes with ordered blocks and tags. `build_ingest_request_from_aternum_node()` turns that node into the same `IngestDocumentRequest` shape by extracting text from fields such as `text`, `body`, `caption`, `description`, `transcript`, `url`, and `path`.

After either ingest path:

1. `ingest_document()` checks whether the same `source_system + source_id` already exists.
2. If it exists, the old document and chunks are replaced.
3. `split_text_into_chunks()` breaks the text into word chunks.
4. `embed_passages()` loads `intfloat/e5-base-v2` and embeds each chunk with the E5 `passage:` prefix.
5. One `Document` row is stored with source IDs, tags, owner/profile IDs, and document metadata.
6. One or more `DocumentChunk` rows are stored with chunk text, `vector(768)` embedding, token estimate, and chunk metadata.

Search uses `POST /api/rag/query`.

1. The query is embedded by `embed_search_query()` with the E5 `query:` prefix.
2. Postgres/pgvector compares the query vector to `DocumentChunk.embedding` using cosine distance.
3. Results are sorted closest-first and limited by `top_k`.
4. `apply_search_filters()` first applies PDF-style visibility filtering, then narrows with optional tag filters.
5. The API returns matching chunks, scores, document metadata, chunk metadata, and a simple extracted "Retrieved context" answer.

Search requests must include a fully resolved `viewer` object validated by `ViewerPermissionContext` in `backend/app/permissions.py`. In the real system this should come from ABE, because ABE owns users, relationships, profiles, circle membership, and tag resolution.

The current "answer" is not generated by an LLM. It is only a readable summary of the top retrieved chunks.

## Aternum Integration Payload

The connector accepts nodes shaped around the provided schema: node fields, ordered blocks, and tag names such as `circle:*` and `profile:*`.

```bash
curl -X POST http://localhost:8000/api/integrations/aternum/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "nodes": [
      {
        "id": "node-001",
        "title": "Family trip",
        "type": "memory",
        "blocks": [
          { "type": "text", "order": 0, "content": { "text": "We visited Vancouver together." } }
        ],
        "tags": [
          { "name": "circle:my_family:00000000-0000-0000-0000-000000000002", "type": "circles" },
          { "name": "profile:00000000-0000-0000-0000-000000000002", "type": "sharing" }
        ]
      }
    ]
  }'
```

## Permission Boundary

`backend/app/permissions.py` mirrors the PDF's `scopeVisibleTo()` checks:

1. Own content: `document.user_id == viewer.user_id`.
2. Connected author + matching `circle:*` tag.
3. Connected author + `profile:*` mention tag for one of the viewer's owned profiles.
4. Circle membership catch-all across all circle tags the viewer holds.

The current sandbox stores tag names directly on `Document.tags`, so `document_has_any_tag()` is a temporary adapter over that field. When the real Aternum database exists, replace that helper with proper `tags`/`taggables` joins and tag type checks. Keep the four visibility checks and their order.

The RAG service does not derive viewer context itself. The caller must pass the Pydantic `ViewerPermissionContext` fields:

- `user_id`
- `owned_profile_ids`
- `circle_tags`
- `connected_profile_ids`
